## What this change does

The sign-in screen now looks for Lichtspiel servers with a Plex-style UDP search on port 32414. It checks each answer against `/api/status` and lists the servers it finds. The sign-in token moves from the plain settings into the system keychain, with a one-time move for older installs and a fallback to the plain setting when the keychain fails. The app also gains a macOS target (sandbox entitlements, Podfile, Xcode project), phone layouts (an overflow menu in the top bar, a search field in the title, touch controls in the player), in-app downloads on iOS and macOS, and a system image picker for poster uploads.

## Should fix

### C1. "Back 10 s" in the first 10 seconds jumps to the end of the video

Status: Fixed in `00fed70`.

- Where: `lib/screens/player.dart:822`. The same pattern already exists for the left-arrow key at `:802`.
- Category: bug
- Problem: the new touch button seeks to `position - 10 s` without clamping at zero. media_kit hands a negative value straight to mpv as an absolute seek, and mpv reads a negative absolute time as "counted from the end".
- Scenario: a phone user starts a film, misses the first line, and taps the replay-10 button at 0:04. `player.seek(-6 s)` sends `seek -6.0000 absolute` (media_kit `lib/src/player/native/player/real.dart:714-716`). mpv jumps to 6 s before the end, so the user lands in the end credits, and progress reporting may then mark the item as watched. media_kit's own double-tap seek clamps (`material.dart:747`, `:1407`), but this custom button does not.
- Smallest fix: `player.seek(player.state.position - const Duration(seconds: 10) < Duration.zero ? Duration.zero : player.state.position - const Duration(seconds: 10))`, or a tiny `back10()` helper used by both line 802 and line 822.
- Docs: mpv manual, `seek` command: "absolute — Seek to a given time (a negative value starts from the end of the file)."
- Confidence: confirmed (media_kit source plus mpv docs)

### C2. An interrupted download leaves a truncated file under the real name

Status: Fixed in `00fed70`; follow-up `bdcc8c1` (a short file is no longer renamed when the server ends the stream early).

- Where: `lib/screens/downloads.dart:86-115` (`_download`)
- Category: bug (data integrity)
- Problem: the file is written straight to its final name (`Film.mkv`). Cleanup happens only in the `catch` block, so it never runs when the process ends mid-download.
- Scenario (macOS): the user saves a 4 GB film and presses Cmd-Q halfway. `~/Downloads/Film.mkv` stays behind at 2 GB and looks like a finished download. The next save of the same film becomes `Film (2).mkv`.
- Scenario (iOS): the dialog asks the user to keep the app open. If iOS kills the suspended app while it is in the background, the half file stays in the Files app under the final name.
- Smallest fix: write to `'${f.path}.part'` and call `rename(f.path)` after `sink.close()` when the download was not cancelled. The `exists()` loop still checks the final name. This is about 3 lines.
- Confidence: confirmed (code path)

## Nice to have

### C3. If both stores hold a token, the older keychain token wins and the newer one is deleted

Status: Fixed in `00fed70`.

- Where: `lib/api.dart:37-54` (`_readToken`)
- Category: bug
- Problem: `save()` writes the plain setting only when the keychain write fails, so a token found in both places means the plain-setting token is the newer one. `_readToken` returns the keychain value whenever it exists, then runs `p.remove('token')` and drops the newer token.
- Scenario: this is most realistic on the ad-hoc signed Mac build (`CODE_SIGN_IDENTITY = "-"`, legacy keychain). Token A sits in the keychain and later expires (main.dart sends the user to sign-in on a 401 but never clears it). After a rebuild, the user signs in again and gets token B. The keychain write is denied at the access prompt, so B goes to the settings. On the next start the keychain read is allowed, so `_readToken` returns A and deletes B. The result is a 401 and the sign-in screen again.
- Smallest fix: when `old != null` and `t != old`, try to write `old` to the keychain and use it. That means changing `if (t == null)` to `if (t != old)`.
- Docs: flutter_secure_storage v11.2.0 README confirms that `MacOsOptions(usesDataProtectionKeychain: false)` uses the legacy keychain without an entitlement. The keychain access prompt after a re-sign is standard macOS behaviour for legacy keychain items, and the docs did not cover it.
- Confidence: plausible (needs a keychain write failure while reads work)

## Checked and not reported

- **iOS discovery finds nothing without the multicast entitlement.** Confirmed by Apple TN3179 and the `com.apple.developer.networking.multicast` docs. The new README already says this and tells the user to type the address, so it is a recorded decision, not a defect.
- **macOS sandbox entitlements.** Apple's docs say UDP needs both `network.client` and `network.server` to receive replies, and both are present. Downloads read-write and user-selected read-only are present. The multicast entitlement is not needed on macOS.
- **The keychain on Mac without Keychain Sharing.** `usesDataProtectionKeychain: false` is what flutter_secure_storage 11.2.0 documents for this case, so it is correct.
- **The back arrow on the mobile player in fullscreen** (`Navigator.maybePop`). media_kit's fullscreen route wraps a `PopScope` that runs the native exit (`fullscreen_inherited_widget.dart:64`), so this only leaves fullscreen as expected.
- **Download cancel and the Escape key on macOS.** Cancel closes the client, the stream errors, and the partial file is deleted. Escape does not close the dialog, because Flutter's `_DismissModalAction` respects `barrierDismissible: false`.
- **iOS HEIC posters.** image_picker_ios re-encodes non-JPEG/PNG/GIF to JPEG (`ImagePickerMetaDataUtil.swift`), and the server sniffs magic bytes anyway.
- **Discovery against the server.** The packet format, `Port` and `Resource-Identifier` headers, reply to the sender, `/api/status` without auth returning `machine_id`, and the http→https fallback on the same port all match `src/gdm.rs`, `src/routes.rs:272-274` and `src/main.rs:94-96`.
- **Content-Disposition parsing** matches `handlers::attachment` (`filename*` first). `/`, `\` and `:` are replaced.

## Full-client audit: checked and not reported

- **Request and response shapes against the server.** I checked every client path in lib/ against `route()`: playlists (entries are item ids, `move?after=` semantics, `editable`/`kind`/`thumbs`), users PATCH fields, `/api/me*` bodies (`old`/`new`, `full_name`, prefs as strings), 2FA, tokens, invites, downloads (`/retry`, `?part=`), maintenance (`before`/`after`, `freed`), preroll (`urls`), together (`seq`, `members`, `item`), chapters (`start` as an integer in ms), `/library/sections/{id}/all?start&size` (`totalSize`), merged versions (`Media[].id` is an item id, and timeline and scrobble map a version to its main item). All match.
- **Android cleartext http.** Flutter's 2.0 rule that blocked plain-HTTP connections on Android and iOS was reverted in 2.2 (Flutter docs, breaking-changes index), and libmpv has its own network stack. iOS already has `NSAllowsLocalNetworking`.
- **Library paging race.** `gen` drops late answers, and `loading` always ends up false on both orders.
