## High

### X1. Wildcard CORS plus LAN-trust lets a browser on the home network act for a PIN-less profile (admin if "no sign-in networks" is set)

Status: Fixed in `c4f405f`.

- **Where:** `src/server.rs:1803-1810` (`base_headers` sends `Access-Control-Allow-Origin: *` on every response), `src/server.rs:2498` (`OPTIONS` answers 204 with those headers), `src/server.rs:2441-2452` (request body parsed as JSON regardless of Content-Type), `src/handlers.rs:145-182` (`home_profiles`/`home_login` gate only on `ctx.is_local()`), `src/server.rs:2484-2488` (`no_auth_networks` callers are treated as the first admin). The `Origin` and `Host` headers are never consulted.
- **Attacker / trigger:** an unauthenticated remote site, loaded in the browser of any person sitting on the LAN. No credentials needed.
- **Impact:** a site the victim visits can reach the server at its LAN address, enumerate home profiles via `GET /api/home`, obtain a token for any PIN-less profile via `POST /api/home/{id}/login`, and then read the returned token because the response is world-readable (`ACAO: *`). With that token it drives the full API. If the admin enabled `no_auth_networks` for the LAN range, every request from that range is already the first admin, so the site gets admin API access with no login step at all. This is drive-by account takeover from the browser.
- **Confirmed:** live — `POST /api/home/8/login` with `Origin: https://evil.example` returned a working token and `ACAO: *`; `GET /api/home` listed the PIN-less "kid" profile cross-origin.
- **Smallest fix:** do not reflect/`*` credentials-bearing data to any origin. Either (a) drop `Access-Control-Allow-Origin: *` from the default headers and echo it only for a configured allow-list, or (b) refuse state-changing/token-returning routes when `Origin` is present and not same-origin. Independently, require same-origin (or a non-simple header) for `/api/home*` so a plain cross-site POST can't reach it, and reconsider auto-admin for `no_auth_networks`.
- **Rating:** High (Critical where `no_auth_networks` is configured) — unauthenticated, no user interaction beyond opening a page.

### X2. Unbounded request-header size: a single slow connection grows server memory without limit

Status: Fixed in `2c4141c`.

- **Where:** request headers are read by tiny_http before `handle` runs; `read_next_line` in `tiny_http-0.12.0/src/client.rs:80-101` appends bytes to a `Vec` with no cap (only the 4 MB cap in `src/server.rs:2443` applies, and only to the *body*, after headers are parsed). One thread per request (`src/server.rs:2126`).
- **Attacker / trigger:** any unauthenticated client that can open a TCP/TLS connection (LAN, or internet via relay/reverse proxy).
- **Impact:** memory exhaustion / OOM. A single connection that streams one never-terminated header line is held entirely in RAM.
- **Confirmed:** live — streaming ~300 MB into one unterminated header raised the process RSS from ~24 MB to ~332 MB, roughly 1:1, while the server kept answering. Several such connections in parallel would exhaust memory and, on the Synology, trigger the OOM killer (or the deploy health-check rollback). Thread-per-request also means many slow connections each cost a thread.
- **Smallest fix:** tiny_http 0.12 has no header-size limit, so enforce it in front of the app — a reverse proxy with header/time limits, or a connection read timeout plus a cap. At minimum document that the server must sit behind a proxy and never be exposed directly. A read timeout on accepted sockets also bounds the slow-connection thread cost.
- **Rating:** High — unauthenticated, trivially repeatable DoS.

### X3. Symlinks inside a library folder are followed when serving files, so a restricted user can read files outside the media roots

Status: Fixed in `c4f405f`, `f1dce91`.

- **Where:** `src/scanner.rs:132-154` (the walker matches on `e.file_type()`/`is_video`/`SUBTITLE_EXTENSIONS` and never rejects symlinks or canonicalizes), `src/handlers.rs:456-497` (`serve_file`/`serve_file_as` open the stored path directly), subtitle path in `src/handlers.rs:642-706`. `delete_media` (`src/actions.rs:391`) and the `refresh ?path=` guard (`src/routes.rs:526`) use `starts_with` on the *stored* path, which a symlink defeats.
- **Attacker / trigger:** anyone who can place a file in a scanned media folder (on a NAS the media share is often writable by household members or other services), or a malicious archive/download unpacked there. The reader can be any signed-in non-admin, including a restricted child profile.
- **Impact:** arbitrary file read with the server's privileges. A symlink named `*.vtt`/`*.srt` or a video extension pointing at `/config/lichtspiel.db`, `/etc/passwd`, another user's files, etc. is scanned in as a subtitle/part and then served through `/library/parts/{id}/subtitles/x0` or `/library/parts/{id}/file`. The subtitle path is the cleanest: it returns the target's bytes as `text/vtt`.
- **Confirmed:** live — a `*.en.vtt` symlink to a secret file was scanned in and its contents returned verbatim over `GET /library/parts/{id}/subtitles/x0` to the non-admin "kid" token.
- **Smallest fix:** in the walker, skip entries whose `file_type().is_symlink()` (or canonicalize and require the real path to stay under a section root). Enforce the same root check with `canonicalize()` in `serve_file` for anything built from scanned paths, and in `delete_media`.
- **Rating:** High — authenticated (any low-privilege account) arbitrary file read; the container runs as root (X6), widening what is readable.

## Medium

### X4. Container runs as root; combined with X3 this reads/writes everything the container can see

Status: Fixed in `cd9586b` (runs as 1026:100).

- **Where:** `Dockerfile` (no `USER`; final stage runs `lichtspiel-server` as root), `docker-compose.yml` and `.gitea/workflows/deploy.yml` (no `user:`/`--user`, mounts `/config` rw and `/media:ro`, adds `/dev/dri`).
- **Attacker / trigger:** combines with any file-read/-write or command bug (X3, or a future ffmpeg/plugin issue).
- **Impact:** every file the server touches is touched as uid 0 inside the container. `/media` is mounted read-only (good), but `/config` is writable and holds the SQLite DB, tokens, plugins and backups; `/dev/dri` is exposed. Running as root removes the last containment layer and makes X3 able to read root-only files on the config volume.
- **Smallest fix:** add a non-root `USER` to the final image stage and `user:`/`--user` in compose and the deploy `docker run`; make sure the data volume is owned by that uid.
- **Rating:** Medium — hardening gap, not directly exploitable alone, but it amplifies several findings.

### X5. The relay trust gap also skips remote bitrate/stream limits and is reachable over plain TCP (worse variant of S3)

Status: Fixed in `c4f405f` (mutual proof); TLS not done.

- **Where:** `src/server.rs:2480-2483` (`relayed => (Some(ip), true)`), `src/relay.rs:179-212` (one-way auth: home proves the secret, the relay proves nothing; link is plain TCP), `src/relay.rs:34-35` (`real_client` is believed fully). Downstream: `src/handlers.rs:388, 433` and `src/server.rs:1616-1618` skip remote caps when `is_local()`.
- **Attacker / trigger:** whoever can answer on the relay address or sit on the plain-TCP path (DNS/route hijack, a compromised or spoofed relay host). S3 already notes the auth gap; the added point is the breadth of what "local" then unlocks.
- **Impact:** by sending `PROXY 192.168.x.y`, such a party makes the connection look local: PIN-less home sign-in, `no_auth_networks` auto-admin, and the bypass of all remote bitrate/concurrent-stream limits (`remote_max_mbps`, `remote_plays_over_limit`). So beyond S3's takeover angle, it is also an unmetered-resource bypass.
- **Smallest fix:** as S3 — a relayed caller is never `is_local()`; add mutual auth (relay answers a nonce too) and prefer TLS on the tunnel.
- **Rating:** Medium — needs a position on the relay path; the trust gap itself is confirmed in code.

### X6. SSRF: admin-triggered server-side fetches to arbitrary URLs with no host/scheme restriction

Status: Fixed in `c4f405f`.

- **Where:** `src/handlers.rs:1156-1180` (`set_image` fetches any `http(s)` URL via `PUT /library/metadata/{id}/image/{slot}`), `src/plexsync.rs:160` (the Plex server URL is admin-supplied and fetched), metadata fetches in `src/metadata.rs`. No allow-list, no block of private/loopback/link-local/metadata-IP targets; redirects are followed by ureq's default.
- **Attacker / trigger:** an admin account (so lower reach), but on a NAS the admin's browser session is the same CSRF target as X1, so X1 + this chains to unauthenticated-origin SSRF.
- **Impact:** the server fetches attacker-chosen internal URLs (router admin pages, cloud metadata endpoints, other LAN services) and, for `set_image`, returns up to 8 MB of the response body if it parses as an image; even when it doesn't, timing/error differences leak reachability.
- **Smallest fix:** for `set_image`, resolve the host and refuse private/loopback/link-local/ULA addresses and non-80/443 ports, and cap redirects (or disallow them). Same guard for the plexsync URL where feasible.
- **Rating:** Medium — admin-gated, but CSRF-reachable via X1 and useful for internal recon/data theft.

## Low

### X7. Tokens travel in URLs (`?token=`) and are built into stream/preroll URLs

Status: Fixed in `23857bf` and `fa82202` (tokens out of URLs); `17af37a` (stored only as a SHA-256 hash, old ones converted on start and on restore). `?token=` is still accepted, see "Known limits".

- **Where:** `src/server.rs:2437-2440` (accepts `?token=`), `src/routes.rs:1147-1170` (decision URLs embed `&token=`), `src/handlers.rs:1255` (preroll URLs embed `?token=`). Tokens are 20 random bytes, stored in plaintext in the DB, never hashed.
- **Impact:** tokens land in proxy logs, browser history, `Referer` headers to third-party poster hosts, and shared links. Not logged by this server's own `server.log` (checked), but the URL surface is wide. Stored-plaintext means a DB read yields live tokens.
- **Fix:** prefer header auth; if `?token=` must stay, set `Referrer-Policy: no-referrer`; consider storing only a hash of the token.
- **Rating:** Low.

### X8. No CSRF protection on any state-changing route beyond the token check

Status: No action: covered by `c4f405f`, which refuses cross-site requests on home routes and on every call that changes something.

- **Where:** all `POST/PUT/PATCH/DELETE` arms in `src/routes.rs`; bodies are accepted as form posts (`src/server.rs:2446-2450`), which are CSRF-friendly simple requests.
- **Impact:** standalone this is mostly covered because mutations need a token the attacker lacks — but it is exactly what makes X1 (and the `no_auth_networks`/relay auto-admin paths) so damaging, since those paths need no token. Worth a same-origin check on mutations as defence in depth.
- **Rating:** Low (elevated in combination).

### X9. No security response headers (CSP, X-Content-Type-Options, X-Frame-Options, Referrer-Policy)

Status: Fixed in `c4f405f` (all four headers).

- **Where:** `src/server.rs:1803-1810` (`base_headers`) and the HTML response at `src/routes.rs:257-266`.
- **Impact:** the SPA has no CSP; the app can be framed (clickjacking) and MIME-sniffed. The server name is HTML-escaped into the page (`routes.rs:261`) and the placeholder SVG is escaped (`server.rs:2988`), so no obvious reflected-XSS sink was found, but the missing headers remove defence in depth.
- **Fix:** add `X-Content-Type-Options: nosniff`, a frame-ancestors CSP (or `X-Frame-Options: SAMEORIGIN`), and `Referrer-Policy: no-referrer`.
- **Rating:** Low.

### X10. Watch-together and invite codes are short (`random_hex(4)` = 32 bits; invites `random_hex(12)`)

Status: Fixed in `17af37a` (64-bit codes; still no rate limit, which 64 bits make unnecessary).

- **Where:** `src/actions.rs:468` (together code 4 bytes), `src/routes.rs` invite creation (`random_hex(12)`). Together rooms expose `can_see_item`-checked content and member names; codes are guessable/enumerable and have no rate limit on `GET /api/together/{code}`.
- **Impact:** a signed-in user can enumerate active watch-together rooms (membership/title disclosure, join another household member's session). Invites at 96 bits are fine.
- **Fix:** widen the together code to ≥8 bytes and/or rate-limit lookups.
- **Rating:** Low.

### X11. `/:/rate`, `/:/scrobble`, favorite, watchlist, continue/remove skip `can_see_item` (route-table extension of S12)

Status: Fixed in `c4f405f` (with S12).

- **Where:** `src/routes.rs:1214-1281` — `rate`, `scrobble`/`unscrobble`, `favorite` only check `items.contains_key`; `watchlist` and `continue/remove` check existence but (watchlist) goes through `set_watchlist` which *does* check — so favorite/rate/scrobble are the leaks. Confirms and slightly widens S12.
- **Impact:** a restricted profile can write watch state and (via scrobble) push titles it may not see into history and to the Trakt plugin, and can probe which ids exist (404 vs 200).
- **Fix:** add `db.can_see_item` to these arms (as S12 says).
- **Rating:** Low.

### X12. GDM UDP discovery (32414) answers any sender and can be used as a small reflector

Status: Fixed in `17af37a` (answers only private, loopback and link-local addresses, IPv6 ULA/link-local, and the "home network" setting).

- **Where:** `src/gdm.rs:40-47` — replies to any `M-SEARCH` with a ~150-byte description to the source address; `recv_from` into a 1024-byte buffer, no rate limit, no source check.
- **Impact:** on the LAN only (not routed off-net normally). A spoofed-source M-SEARCH makes the server send its description to a victim — a minor reflection/amplification and a server-name/-id disclosure to anyone on the segment. Low because it is LAN-scoped and small.
- **Fix:** optional — ignore packets from off-subnet sources; it is already gated by `gdm_enabled`.
- **Rating:** Low.

### X13. PBKDF2 at 60k rounds of HMAC-SHA256, hand-rolled; TOTP/HMAC also hand-rolled

Status: No action: no break found, the RFC 6070 test vector passes and comparisons are constant-time; with tokens now hashed (`17af37a`) a stolen file gives nothing to sign in with.

- **Where:** `src/auth.rs:5-57` (PBKDF2, constant-time compare present and correct), `src/totp.rs` (hand-rolled SHA-1/HMAC/TOTP). The RFC6070 test vector passes (`auth.rs:78`).
- **Impact:** 60k SHA-256 rounds is on the low side for 2026 but acceptable for a home server; the real risk is maintenance (hand-rolled crypto). No concrete break found. The password compare and the relay/TOTP compares are constant-time (verified). Login has a 400 ms delay and per-user/per-IP lockout (`handlers.rs:50-74`).
- **Fix:** none urgent; consider raising rounds and/or a vetted crate.
- **Rating:** Low.

### X14. Token `last_ip`/`last_device` are set from client-controlled headers without sanitising

Status: Fixed in `17af37a` (device names cut to 100 characters; the web app still draws them as text only).

- **Where:** `src/server.rs:2457-2463` — `last_device` from `device_label` (X-Plex-* headers, User-Agent) and `last_ip` from `peer`, stored and later shown in the tokens list (`routes.rs:1607`) and dashboard. These are rendered by the SPA.
- **Impact:** if the SPA ever inserts these as HTML, it is stored-XSS fodder; the web-app review should confirm the render path escapes them. Server-side they are just stored.
- **Fix:** the web app should treat them as text; optionally length-cap/sanitise server-side.
- **Rating:** Low (depends on the web renderer — flagged for the web-app auditor).

### X15. `browse` (file picker) and `restore` are admin-only but `browse` lists any absolute path

Status: No action: admin-only and expected for a folder picker; the X1 path that made it reachable is closed in `c4f405f`.

- **Where:** `src/routes.rs:1870-1873` + `src/handlers.rs:955-994` (`GET /api/browse?path=` lists any directory on the host, admin-only), `src/maintenance.rs:163-166` (restore name is validated against traversal — good).
- **Impact:** admin-only directory enumeration of the whole host filesystem (expected for a folder picker, but combined with X1's CSRF-to-admin it becomes reachable). `restore` path traversal is correctly blocked.
- **Fix:** none strictly; note it as admin-trusted surface. Mainly a reason to fix X1.
- **Rating:** Low.

### X16. Plugin stdin can block before the timeout loop (confirms S13)

Status: Fixed in `17af37a` (input written on its own thread, so the time limit applies).

- **Where:** `src/plugins.rs:159-176` — `write_all` to the child's stdin happens before the timeout loop in the common path. (The reader threads for stdout/stderr are started *after* the write.) A plugin that fills the pipe before reading blocks the request thread past `timeout_seconds`.
- **Impact:** a signed-in user calling `POST /api/plugins/{id}/call/{action}` with a large body against a plugin that writes-before-reading hangs a request thread. Same as S13; verified the ordering in code.
- **Fix:** start the reader threads first, then write stdin from its own thread.
- **Rating:** Low.
