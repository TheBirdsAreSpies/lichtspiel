Status: all findings handled, see [the review overview](../review-2026-11-15.md).

Scope: `src/*.rs`, `build.rs`, `Cargo.toml`, `Dockerfile`, and `web/` where it talks to the server. `clients/` was left out.

**What this repo does:** Lichtspiel is a single Rust program that replaces Plex. It scans movie and TV folders, gets details online, streams or converts the videos with ffmpeg, and serves a web app and a JSON API. All library data sits in memory behind one `Mutex` (`App.db`) and is written to SQLite.

**Load assumed:** one household on a Synology NAS. That means 1 to 10 accounts, 1 to 5 players at once, a library of 5k to 50k items (movies, shows, seasons and episodes), and sometimes access from outside through a reverse proxy or the relay. Any slow step that holds `app.db` stops every other request while it runs, so lock hold time counts as user-visible delay.

## Must fix

### S1. On every start, the server deletes poster files in the user's media folders when they don't look like a photo

Status: Fixed in `b426f4d`.

- **Where:** `src/server.rs:302-320` (`remove_broken_pictures`), called at `server.rs:287` on every start
- **Category:** bug (data loss)
- **Problem:** The function deletes any `it.poster` / `extra.art` file whose first bytes are not JPEG, PNG, WebP or GIF. The scanner (`scanner.rs:734 find_poster`) sets `it.poster` to files inside the user's media folders (`poster.jpg`, `<movie>.jpg`, `folder.jpg` …).
- **Failure scenario:** A desktop install (Windows/macOS/Linux, media not mounted read-only) has `Movies/Alien (1979)/poster.jpg`, and that file is 0 bytes, an AVIF/HEIC saved as .jpg, or a BMP. On the next start the server deletes the user's file. In Docker, `/media:ro` saves the files by accident. The same loop also calls `items.get_mut` for every item, so `Tracked` marks every item as changed and the first save after each start rewrites every item row.
- **Smallest fix:** Delete only files under `self.data_dir`: add `&& Path::new(p).starts_with(&self.data_dir)` to `bad`. Clear the field without deleting files outside it. Use `db.items.get(&id)` to check, and call `get_mut` only when something changes.
- **Benchmark:** no
- **Confidence:** confirmed (code path read end to end)

### S2. "Clean up" (and the weekly automatic clean-up) empties the whole transcode folder, whatever folder that is

Status: Fixed in `b426f4d`.

- **Where:** `src/maintenance.rs:40-49`, scheduled at `maintenance.rs:291`. The folder comes from `settings.transcode_dir` (`server.rs:389`).
- **Category:** bug (data loss)
- **Problem:** `cleanup` runs `remove_dir_all` / `remove_file` on every entry of `transcode_dir()`. An admin can set that path to any folder ("Folder for live conversions … Pick a fast disk", `web/pages.js:961`).
- **Failure scenario:** The admin sets the folder to `D:\Temp`, `/volume1/scratch` or `/tmp`, because Plex users often point its transcoder at a shared temp folder. The next weekly clean-up while nothing is playing deletes everything in that folder. There is also a race: `idle` is checked once, so an HLS session started between the check and the loop loses its folder.
- **Smallest fix:** Delete only entries that look like this server's sessions (directory names of 32 hex characters, as `hls_start` makes them with `random_hex(16)`), or always work in a `lichtspiel/` subfolder of the chosen folder.
- **Benchmark:** no
- **Confidence:** confirmed

### S3. A caller coming through the relay is believed to be at home if the relay says so

Status: Fixed in `b426f4d`.

- **Where:** `src/server.rs:2469-2483` (`relayed` → `(Some(ip), true)`), `src/relay.rs:179-195` (`wait_for_caller`), `relay.rs:205-211` (`hand_over`)
- **Category:** security
- **Problem:** The home server proves the shared secret to the relay, but the relay never proves anything back. The link is plain TCP. The home server then trusts any `PROXY <ip>` line completely (`remote_trusted = true`). If `ip` is private, `is_local()` is true.
- **Failure scenario:** Anyone who can answer on the relay address (a DNS hijack, someone on the path of the plain-TCP link, or a compromised relay box) sends `NONCE x`, ignores the AUTH reply, sends `OK`, then `PROXY 192.168.1.10`. The home server connects them to its web server as a local caller. Home profiles without a PIN then sign in with no password (`handlers.rs:153`). If `no_auth_networks` covers that range, the caller acts as the first admin (`server.rs:2485-2488`). Remote bitrate and play limits are skipped as well.
- **Smallest fix:** A caller that came through the relay is never local. In `handle`, use `Some(ip) => (Some(ip), !crate::server::ip_is_local(ip))`, or add a `relayed` flag that `is_local()` honours. Mutual auth (the relay also answers a nonce) would be the full fix, but the one-line change is enough.
- **Benchmark:** no
- **Confidence:** plausible (needs control of the relay path; the trust gap itself is confirmed in code)

### S4. "Optimize" can hang for ever, and Cancel does not stop it

Status: Fixed in `b426f4d`.

- **Where:** `src/actions.rs:274-292`
- **Category:** bug / load
- **Problem:** ffmpeg runs with stdout and stderr both piped. The code reads stdout to the end and only then reads stderr. `cancel_job` (`server.rs:810`) only sets `job_cancel`, which is checked between files and never kills the running ffmpeg.
- **Failure scenario:** A damaged file makes ffmpeg print more than about 64 KB of decode errors (with `-loglevel error`, one line per broken frame). The stderr pipe fills, ffmpeg blocks writing to it, stdout (`-progress`) stops, and the reader waits for ever. The job stays "Optimizing" until the server restarts, and other jobs can't start because `app.job` is held. A 3-hour 4K file also can't be cancelled.
- **Smallest fix:** Read stderr on its own thread, as `downloads.rs:336` already does ("stderr is read on the side so a chatty ffmpeg never blocks"). Inside the stdout loop, kill the child when `app.job_cancelled()`.
- **Benchmark:** no
- **Confidence:** plausible (the pipe deadlock is standard behaviour; the trigger needs a chatty ffmpeg). The missing cancel is confirmed.

### S5. Rows that can't be read are "kept in the file", but the next full write deletes them

Status: Fixed in `b426f4d`.

- **Where:** `src/store.rs:287-296` and `306-308` (load skips bad rows), `store.rs:371-373` and `394-396` (`delete from items` / `delete from views` when `*_all`), `src/server.rs:359-365` (a failed save calls `mark_all`)
- **Category:** bug (data loss)
- **Problem:** `load` logs "it is skipped and kept in the file as it is". Any later write with `items_all` (after one failed save, a restore, or a first start from JSON) runs `delete from items` and writes back only the items in memory. The skipped rows disappear.
- **Failure scenario:** CI rolls back to `lichtspiel:previous` after a release that added a new `ItemKind` or enum value. The old binary can't read those items and skips them. One save then fails (disk full, or `SQLITE_BUSY` past 10 s during a `vacuum into` backup). rusqlite rolls the transaction back (the rusqlite docs confirm it), `mark_all` is set, the next save deletes all item rows and rewrites only the readable ones, and the new items are gone for good. Separately, the scanner sees those files as unknown and adds them again under new ids, so they come back as duplicates after an upgrade.
- **Smallest fix:** Don't use `delete from items` / `delete from views` for `*_all`. Write every row with `insert or replace`, then delete only the ids that `Store` saw at load and that are no longer in memory. Or keep the set of unreadable ids and exclude them from the delete: `delete from items where id not in (…)`.
- **Benchmark:** no
- **Docs:** rusqlite `Connection::transaction`, "defaults to rolling back when it is dropped"
- **Confidence:** confirmed (code path). The trigger needs a rollback plus one failed write.

## Should fix

### S6. Every save serializes the whole play history and play statistics while holding the library lock

Status: 0.330 ms.

- **Where:** `src/store.rs:181-196` (`Changes::take`), called with `app.db` held at `server.rs:358`. Sizes: `db.rs:672` `HISTORY_MAX = 20000`, `db.rs:688` `SESSIONS_MAX = 50000`.
- **Category:** perf / load
- **Problem:** Every save serializes all 14 small parts with `serde_json::to_string`, including `history` (up to 20k events) and `sessions` (up to 50k), only to compare them with what was written last time. `timeline` (`handlers.rs:357`) saves on every player report, about every 10 s per player, and dozens of other routes save too.
- **Failure scenario:** A long-running server reaches the limits. Each save then builds roughly 5 MB of JSON (about 70 bytes × 70k entries, an ESTIMATE) under `app.db`. On a NAS CPU that can be tens of ms per save, and every other request waits behind it. With 3 players reporting plus browsing, the web app stutters.
- **Smallest fix:** Keep a cheap fingerprint for `history` and `sessions`, such as `(len, last.at, last.item_id)`, and serialize them only when it changes. Better, give `Db` a `history_dirty` / `sessions_dirty` flag that `record_play_at` / `record_session` set.
- **Benchmark:** **yes.** Add a `#[test] #[ignore]` that fills a `Db` with 20k history and 50k sessions and times `Changes::take` in release (`cargo test --release -- --ignored changes_take_cost`). Or log `Changes::take` duration in `try_save` and run `--self-test`.
- **Confidence:** confirmed (code). The size of the delay needs the benchmark.

### S7. "Unwatched" / "In progress" filters on a TV library rescan the whole library for every show

Status: 4.12 ms.

- **Where:** `src/query.rs:316-323` (`watched_container`) and `query.rs:375-379` (`unwatched_leaves`), via `db.leaves` → `db.children` (`db.rs:1380-1410`), which runs `items.values().filter(parent == x)` over all items for each level. Called per item from `matches_all` (`routes.rs:1521`, `routes.rs:1950`) and from smart playlists.
- **Category:** perf
- **Problem:** For each show, `leaves` makes one full pass over the library per show and per season. So the cost is O(shows × (1 + seasons) × items), and `db.view` adds a `format!` string allocation for each leaf.
- **Failure scenario:** 1,000 shows with 5 seasons each in a 50k-item library is about 1,000 × 6 × 50,000 = 300M item visits (ESTIMATE). That can take seconds per request, all with `app.db` locked. The web app sends `unwatched_leaves` by default for a show section with the old "unwatched" setting (`web/app.js:677`). Sorting already precomputes keys (`query.rs:600+`); filtering does not.
- **Smallest fix:** Build `server::Index` once per filter or sort call (it already exists, `server.rs:2532`) and pass it into `field`, or compute the leaves of each container once in a `HashMap` before the `retain`.
- **Benchmark:** **yes.** Generate a library like the self-test does with a few hundred shows, time `GET /library/sections/{tv}/all?unwatched_leaves=1` before and after, and check the `Server-Timing` header (`server.rs:2501`) or the "Slow answer" log line.
- **Confidence:** confirmed (complexity read from code)

### S8. Every scan of a movie library compares each extra with every item, all while holding the library lock

Status: 3.29 ms.

- **Where:** `src/scanner.rs:1120-1142` (pass 1 of `scan_section_in`)
- **Category:** perf / load
- **Problem:** For each extra file (trailer, featurette …), the code walks every item in the library, makes a `Path` for each, and compares parents. All of it runs inside one `with_db` closure, so `app.db` stays locked for the whole loop. It also runs on every scan, even when no file changed, because the list is built before the "changed?" check.
- **Failure scenario:** 5,000 movies with 3,000 extras is 15M path comparisons (ESTIMATE). Each scheduled scan then freezes all requests for about a second or more on a NAS. The "Slow answer" log would show it on unrelated routes.
- **Smallest fix:** Before the loop, build `HashMap<PathBuf /*movie dir*/, Vec<(u64 id, String stem)>>` in one pass, then look each extra up there. Skip the pass for extras that are unchanged and already known (`known_extras`).
- **Benchmark:** **yes.** Write a timed test with a generated tree (N movie folders, each with `Trailers/x.mkv`) that calls `scan_section_in` with a no-op ffprobe, measures the time spent inside `with_db`, and compares before and after.
- **Confidence:** confirmed (code). The size of the delay needs the benchmark.

### S9. Posters, backgrounds and seek-bar pictures start any number of ffmpeg processes, and other requests can read a half-written picture

Status: Fixed in `f1dce91`.

- **Where:** `src/handlers.rs:785-795` (`art`), `handlers.rs:888-903` (`thumb`), `handlers.rs:908-918` + `937` (`make_frame` / `frame`)
- **Category:** load / bug
- **Problem:** When no cached picture exists, each request runs ffmpeg synchronously on its own thread with no limit. The limit of two in `scaled_poster` (`handlers.rs:810-836`) does not cover these paths, even though its own comment explains why a limit is needed. ffmpeg also writes straight to the final cache file, with no temp file and rename.
- **Failure scenario:** After a fresh import with no online posters, the library page asks for 100 thumbs at once and starts 100 ffmpeg processes on the NAS. Moving along the seek bar starts one ffmpeg for each 10-second step. A second request for the same poster sees `len() > 0` while the first ffmpeg is still writing, gets a cut-off JPEG, and the browser keeps it for an hour (`with_cache`). If the server stops in the middle of a write, the cut-off file stays for up to a week.
- **Smallest fix:** Reuse the `RESIZING` pattern: a small shared semaphore (at most 2 to 4 at a time; when it is full, return the placeholder SVG or a 503 for frames) and write to `*.tmp.jpg`, then rename, as `scaled_poster` already does.
- **Benchmark:** no (a load issue; check with 50 parallel `curl` calls to `/library/metadata/{id}/thumb` on items without posters)
- **Confidence:** confirmed (code). The impact is plausible.

### S10. Anyone signed in can start any number of HLS remux sessions, and the transcode limit can be overshot

Status: Fixed in `f1dce91`.

- **Where:** `src/handlers.rs:510-527` (`check_transcode_allowed` counts only `Method::Transcode`), `handlers.rs:603-640` (`hls_start`), `handlers.rs:572-600` (`progressive`)
- **Category:** load
- **Problem:** Remux sessions (when direct play is possible, `Direct` is turned into `Remux`) have no limit at all. Each one is an ffmpeg process writing the whole file to the transcode folder, and it lives 90 s after the last request. The transcode limit is checked first and the session is inserted later (`handlers.rs:628`), so parallel starts all pass the check.
- **Failure scenario:** A player that retries (or a script) calls `start.m3u8` 20 times in a few seconds. That starts 20 ffmpeg remuxes filling the disk, plus the same number of transcodes if they all arrive before the first insert.
- **Smallest fix:** Cap all ffmpeg sessions per user (for example, at most 3 `hls` + `progressive` entries for one `user_id`). Do the limit check and the insert while holding `app.hls` once (reserve the slot first, then spawn).
- **Benchmark:** no
- **Confidence:** plausible

- **Category:** tests
- **Problem:** Access is enforced by where a match arm sits and by about 80 hand-written `if !admin { return need_admin(); }` lines. A new arm put in the open block, or a forgotten admin check, shows up in no test. The self-test checks one `unauth == 401`.

- **Smallest fix:** One unit test: build a test `App`, then for every `ROUTES` entry outside a short allow-list, call `route()` with `user: None` and assert 401. Call it again with a non-admin user for paths whose description starts with "Admin:" and assert 403. The data already exists in `ROUTES`.

## Nice to have

### S13. A plugin that doesn't read its input can hang a request past its timeout

Status: Fixed in `17af37a` (input written on its own thread, so the time limit applies).

- **Where:** `src/plugins.rs:161-176`
- **Category:** bug / load
- **Problem:** The event JSON is written to stdin with `write_all` before the stdout/stderr reader threads start and before the timeout loop. A plugin that prints before reading, or never reads, blocks `write_all` once the input is larger than the pipe buffer (about 64 KB). The `timeout_seconds` kill is never reached.
- **Failure scenario:** `POST /api/plugins/{id}/call/{action}` with a 200 KB body (any signed-in user; `handle` accepts up to 4 MB) to a plugin that writes a log line first. The request thread hangs for ever.
- **Smallest fix:** Start the two reader threads first, then write stdin from its own thread (or after the readers start), so the timeout loop always runs.
- **Benchmark:** no
- **Confidence:** plausible

### S14. The same two-step code can be used twice by parallel sign-ins

Status: Fixed in `17af37a` (checked and recorded under one lock).

- **Where:** `src/handlers.rs:95-102`
- **Category:** security (low)
- **Problem:** "Is this code step fresh?" and "remember this step" take the `USED_STEPS` lock separately (check, then write).
- **Failure scenario:** Someone who saw a password and a code sends two sign-ins at the same moment. Both pass the freshness check and both get a token.
- **Smallest fix:** Do the check and the insert under one `USED_STEPS` lock guard.
- **Benchmark:** no
- **Confidence:** plausible

### S15. Any signed-in user can grow the problem-report list without limit

Status: Fixed in `17af37a` (at most 50 open reports per person, then 429; German text in de.js).

- **Where:** `src/actions.rs:55-68`
- **Category:** load (low)
- **Problem:** There is no cap and no rate limit. Each report can hold up to 2,000 characters, and the whole `reports` list is serialized on every save (see S6).
- **Failure scenario:** A script posts 100k reports, which adds about 200 MB to every save and to memory.
- **Smallest fix:** Keep at most N open reports per user (for example 50), or cap the whole list the way `HISTORY_MAX` caps history.
- **Benchmark:** no
- **Confidence:** confirmed
