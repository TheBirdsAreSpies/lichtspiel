# Plugins and deploy review, 2026-11-15

Status: all findings handled, see [the review overview](../review-2026-11-15.md).

Date: 2026-11-15. Branch `review/ponytail-fixes` (HEAD f3ac72e). No code changed. Nothing deployed or pushed.

**What this repo does:** Lichtspiel is a self-hosted video server (a Plex replacement), shipped as one Rust binary in a Docker image that runs on a Synology NAS. Three bundled Python plugins (nfo-reader, trakt, webhook-notify) are started as separate programs for each event, and get one JSON message on standard input. Every push to `main` is tested, built and deployed on the NAS by a Gitea runner.

**Load assumed:** one household. A handful of users and players at once, a library of up to tens of thousands of files, and one NAS. Deploys come from one person, a few times a day.

**How it was checked:** I read every line in scope: the 3 plugins with their `plugin.json`, `Dockerfile`, `docker-compose.yml`, `.gitea/workflows/deploy.yml`, `.gitignore` and `.dockerignore`. I also read the calling side (`src/plugins.rs`, `fire`/`lookup_metadata`/`install_bundled_plugins` in `src/server.rs`, `plugin_call` in `src/handlers.rs`, the plugin routes, the TLS/bind code in `src/main.rs`, and `src/gdm.rs`). The plugins have no tests. `python3 -I -m py_compile` passes on all three files. I ran the scenarios below on copies of the plugins, against a local test HTTP server, using macOS system Python 3.9.6 with expat 2.2.8. Docker is not installed on this machine, so nothing was run inside the image.

Severity: **Must fix** (bug, security, data loss, breaks at the expected load) > **Should fix** > **Nice to have**. Confidence: **confirmed** (reproduced, or the code path is unambiguous) / **plausible** (depends on a condition I could not observe).

## Must fix

### D1. A failed `docker run` leaves no container running, and the rollback never runs

Status: Fixed in `cd9586b`.

- **File:** `.gitea/workflows/deploy.yml:56-65, 75`
- **Category:** Bug / availability (rollback).
- **Problem:** `start()` first runs `docker rm -f lichtspiel` and then `docker run`. Gitea runner `run:` steps use the default bash flags, like GitHub's `bash -e`, so a failing command outside an `if` ends the step at once. `start ${NAME}:latest` on line 75 is outside the `if`. If `docker run` fails there, the script exits before `healthy`/rollback is reached, and the old container is already gone.
- **Failure scenario:** After a DSM update `/dev/dri` is gone (or the port is taken, or a mount path is wrong in a Gitea variable). `docker run --device /dev/dri:/dev/dri …` exits with 125. The step fails, no `lichtspiel` container exists, and the server stays down until someone deploys by hand.
- **Smallest fix:** Make the start part of the check. Change line 75-76 to `if start ${NAME}:latest && healthy; then`. Under `-e`, a failure inside an `if` condition doesn't end the script, so the `else` branch (diagnostics plus rollback) runs.
- **Source:** Gitea runner docs (docs/job-hooks.md: "the shell flags applied to `run:` steps …, as on GitHub"; act `step_run.go` picks bash by default). GitHub's documented default for bash is `bash -e {0}`.
- **Confidence:** confirmed by reading (not run on the NAS).

### D2. The health check only speaks plain HTTP to 127.0.0.1:8484, so HTTPS or a chosen network card makes every deploy "fail"

Status: Fixed in `cd9586b`.

- **File:** `Dockerfile:42`; also `src/main.rs:86-94` (TLS and `bind_address` come from Settings)
- **Category:** Bug (deploy and monitoring).
- **Problem:** The check is `urlopen('http://127.0.0.1:8484/identity')`. If an admin turns on HTTPS in Settings (cert/key paths), the main port speaks TLS and plain HTTP fails. If the admin picks a network card under Settings (`bind_address`), the server no longer listens on 127.0.0.1.
- **Failure scenario:** HTTPS is switched on. The container reports `unhealthy` forever. Each push: the new version never turns healthy → rollback to `previous` → that one is just as "unhealthy" but stays running, and the job is red. No new version ever stays deployed, even though the code is fine.
- **Smallest fix:** In the deploy, check from outside the container (`curl -fsk https://127.0.0.1:${PORT}/identity || curl -fs http://127.0.0.1:${PORT}/identity`). Or make the HEALTHCHECK try both schemes with an unverified SSL context (`ssl._create_unverified_context()`).
- **Source:** Docker reference (HEALTHCHECK: exit 0 = healthy, 1 = unhealthy; `retries` consecutive failures → unhealthy).
- **Confidence:** confirmed by reading.

### D3. Fixed bundled plugins never reach an existing install

Status: Fixed in `c4f405f` (newer bundled plugins replace their program files and keep the plugin's data).

- **File:** `src/server.rs:1643-1690` (`install_bundled_plugins`); `Dockerfile:36-39`
- **Category:** Bug (update path).
- **Problem:** A bundled plugin is copied into `/config/plugins/` once. After that it is skipped, because its name is in `.bundled-installed` or the folder already exists. A new image has the new `/opt/lichtspiel/plugins`, but the running server keeps executing the old copy under `/config/plugins`.
- **Failure scenario:** Any fix to P1-P5 below is merged and deployed. CI is green and the image contains the fix, but the NAS still runs the old `main.py` with the bug.
- **Smallest fix:** For bundled plugins, overwrite the code files (`*.py`, `plugin.json`) when the bundled `version` in `plugin.json` is newer than the installed one. Never touch other files such as `tokens.json`. Otherwise, document a manual copy step.
- **Confidence:** confirmed by reading.

### P1. Trakt: with Trakt's 24-hour tokens, the token is refreshed on every event, and one lost answer disconnects the user for good

Status: Fixed in `e2f7732`.

- **File:** `plugins/trakt/main.py:154-166` (also 140-142)
- **Category:** Bug / data loss (the user's Trakt login).
- **Problem:** The plugin refreshes when `expires_at - now < 24*3600`. Trakt now issues access tokens that live 24 h (`expires_in` ≈ 86399), so this is always true. Every start, pause, stop and watched event does a refresh first. Each refresh rotates the refresh token. If Trakt handles the refresh but the answer is lost, the new tokens are never saved. The causes can be a 30 s timeout, a network blip, the server killing the plugin, or a crash on `URLError` (P6). The next refresh with the old refresh token then gets 400, and lines 162-164 delete the user's login without telling them.
- **Failure scenario:** I reproduced it: a token with `expires_at = now + 86399` → `access_token()` calls `/oauth/token` at once (the check printed `True`). With an unreachable API the plugin then crashed with a `URLError` traceback (exit 1). In real use, scrobbles stop and the panel says "Not connected" a few days later.
- **Smallest fix:** Refresh only near the real expiry: `< 600` (10 min) instead of `< 24*3600`. Python-pytrakt made the same change. Optionally, on 400 keep the user and mark the login "needs reconnect" instead of deleting it.
- **Source:** Trakt's 2025 change (access tokens 3 months → 24 h) is known only from secondary/community sources: emby.media forum topic 136113, the Trakt forum "I refresh the Token, but i get 90 days", python-pytrakt PR #59/#61. I could not open Trakt's official API docs. The sources disagree on the start date (4 or 20 March 2025).
- **Confidence:** the refresh on every event is confirmed (by running it). The disconnect is plausible (it needs a lost refresh answer).

### P2. Webhook: one bad address or two slow ones stop the messages to all the others

Status: Fixed in `e2f7732`.

- **File:** `plugins/webhook-notify/main.py:22-31`; `plugin.json:14` (`timeout_seconds: 15`)
- **Category:** Bug (crash on unexpected input, blocking).
- **Problem:** (a) `urllib.request.Request(url, …)` is built outside the `try`, so an address without `http://` raises `ValueError` and ends the program. (b) The addresses are tried one after another with `timeout=10` each, but the server kills the plugin after 15 s. That timeout applies to each socket read, not to the whole request, so a server that trickles out its answer slowly keeps the request alive without limit.
- **Failure scenario:** All reproduced:
  - `urls = ["example.com/hook", "http://127.0.0.1:18999/ok"]` → `ValueError: unknown url type`, exit 1, and the second, valid address got nothing.
  - `["…/hang", "…/hang", "…/ok"]` → took 20.3 s. Under the server's 15 s limit the run is killed and `/ok` never gets the message.
  - A slow-drip endpoint was still running after 25 s.
- **Smallest fix:** Move the `Request(...)` line inside the `try`. Use `timeout=4`, or stop starting new addresses once about 12 s have passed. If you want the slow-drip case closed for good, send to the addresses in parallel threads with a shared deadline.
- **Source:** CPython 3.11 docs was used for urllib/etree. The timeout semantics come from the `urlopen` docs ("timeout for blocking operations like the connection attempt").
- **Confidence:** confirmed (reproduced).

## Should fix

### D4. The health-check window is short and coarse; a slow start is killed mid-start and rolled back

Status: Fixed in `cd9586b`.

- **File:** `Dockerfile:42` (`--interval=60s`, no `--start-period`); `deploy.yml:66-74` (45 × 4 s = 180 s)
- **Category:** Risk (data) / scale.
- **Problem:** Docker runs the first check only after one full interval (60 s), so the deploy gets at most 3 checks in its 180 s window. If the server needs longer to open, for example on the first start after a DB migration or on a slow ARM NAS with a big library, the deploy runs `docker rm -f` on the new container while it is still starting. Then it starts `previous`. The rollback restores the image, not the data, so the old version may open a DB that the new one has already changed.
- **Failure scenario:** A start takes 200 s → rollback → `rm -f` kills the server during its first write → the old binary opens the newer DB.
- **Smallest fix:** `HEALTHCHECK --interval=15s …`. `--start-interval` needs Docker Engine 25+, and Synology Container Manager may be older, so don't rely on it. Have the deploy wait for the first check (or call `/identity` itself) and give it 5-10 minutes. Write in the README that a rollback doesn't undo DB changes.
- **Source:** Docker reference ("The health check will first run **interval** seconds after the container is started"; "start interval … requires Docker Engine version 25.0 or later").
- **Confidence:** plausible.

### D5. Finding servers on the home network (GDM) cannot work in the Docker setup

Status: Fixed in `cd9586b` (host networking documented as an opt-in).

- **File:** `docker-compose.yml:8-9`; `deploy.yml:59-63`; `src/gdm.rs:24-44`; `clients/lichtspiel/lib/discovery.dart:13-43`
- **Category:** Bug (feature is broken in the main deployment).
- **Problem:** The client sends its search to multicast `239.0.0.250:32414` and to `255.255.255.255:32414`. The container publishes only TCP 8484 and runs on the default bridge network. UDP 32414 isn't published, and even if it were, Docker's port mapping forwards unicast traffic to the host address, not multicast or broadcast. The `HELLO` announcement on start also stays inside the bridge.
- **Failure scenario:** On the NAS, the new sign-in screen (commit a457208) never lists the server, and users have to type the address.
- **Smallest fix:** Use host networking for this container (`network_mode: host` in compose, `--network host` in `deploy.yml`, then drop `-p`/`ports`). The trade-off is that the port can no longer be remapped. Otherwise, document that discovery is off in Docker.
- **Confidence:** confirmed by reading (not run on the NAS).

### D6. The container runs as root, and so do the plugins and ffmpeg

Status: Fixed in `cd9586b`.

- **File:** `Dockerfile:28-43` (no `USER`); `docker-compose.yml` and `deploy.yml` (no `user:`/`--user`)
- **Category:** Risk (security).
- **Problem:** Everything runs as root: the server, every plugin (`python3 main.py` from `/config/plugins`) and ffmpeg on downloaded media files. Anyone who can write to the `docker` shared folder (SMB) can drop a `main.py` that then runs as root with `/dev/dri` and the network. A bug in an ffmpeg demuxer, triggered by a crafted file, gives root in the container too.
- **Failure scenario:** A crafted `.mkv` exploits ffmpeg → root inside the container, with read/write access to `/config` (the DB, plugin tokens).
- **Smallest fix:** Run as the Synology user: `user: "1026:100"` (or the matching values) in compose and `--user` in `DOCKER_ARGS`. Then `chown -R` `/volume1/docker/lichtspiel` once, and add that user to the `video`/`render` group for `/dev/dri`. Check in the README.
- **Confidence:** plausible (a defence-in-depth gap).

### D7. Every deploy keeps a `lichtspiel:<sha>` image, and nothing ever removes them

Status: Fixed in `cd9586b`.

- **File:** `deploy.yml:52, 90-91`
- **Category:** Scale (disk keeps growing).
- **Problem:** Each build tags `lichtspiel:${GITHUB_SHA::8}`. `docker image prune -f` removes only dangling (untagged) images, so every SHA-tagged image stays. If the Docker on the NAS uses BuildKit, its build cache isn't pruned either.
- **Failure scenario:** A few deploys a day for months → the volume that holds Docker's data fills up → builds and the running server start failing on writes. Each image's own layers are at least the binary plus plugins; I didn't measure the size.
- **Smallest fix:** Stop tagging the SHA (the binary already embeds `GIT_SHA`). Otherwise, in "Tidy up", delete every `lichtspiel:*` tag except `latest` and `previous`.
- **Confidence:** the growth is confirmed by reading; the size is unknown.

### D8. Two copies of the run setup control the same container name

Status: Fixed on 2026-11-21: `deploy.yml` starts the container from `docker-compose.yml` with `docker compose up`, so there is one definition (`cd9586b` had only made them point to each other).

- **File:** `docker-compose.yml:3-24` and `deploy.yml:54-65`
- **Category:** Lean (merge) / Risk.
- **Problem:** Compose and `deploy.yml` each list the mounts, ports, devices and restart policy, and both use the name `lichtspiel`. A change made to one (a new mount, the GDM port from D5) is easy to miss in the other. The CI also runs `docker rm -f` on a container that Compose created.
- **Failure scenario:** A user sets it up through Container Manager → Project (compose), then enables CI. The first deploy deletes the compose-managed container, and Container Manager shows a broken project.
- **Smallest fix:** Pick one. Let `deploy.yml` run `docker compose up -d --no-build` with the image it just built (`image: lichtspiel:latest` in compose), so the mounts live in one file.
- **Confidence:** plausible.

### P3. nfo-reader: a Kodi .nfo with a link after the XML gives no metadata

Status: Fixed in `e2f7732`.

- **File:** `plugins/nfo-reader/main.py:28-32`
- **Category:** Bug (missed edge case).
- **Problem:** Kodi allows (and scrapers write) XML followed by a TMDB/IMDb URL on the next line. `ET.parse` stops with "junk after document element", the error is swallowed, and the file counts as empty.
- **Failure scenario:** Reproduced. `movie.nfo` = `<movie><title>Kodi</title><plot>good plot</plot><year>2001</year></movie>` followed by `https://www.themoviedb.org/movie/603` → the plugin prints nothing.
- **Smallest fix:** Read the text, cut it after the last closing root tag and use `ET.fromstring`. For example: `s = open(path, encoding="utf-8", errors="replace").read(); end = s.rfind(">"); root = ET.fromstring(s[:end+1])`. A safer version cuts at `</movie>`/`</episodedetails>`/`</tvshow>`.
- **Confidence:** confirmed (reproduced).

### P4. nfo-reader: looks for tvshow.nfo in the wrong folder when a show has no season folders

Status: Fixed in `e2f7732`.

- **File:** `plugins/nfo-reader/main.py:22-24`
- **Category:** Bug (edge case).
- **Problem:** The comment says "one or two levels up", but the code checks only the parent of the episode's folder. For `Show/S01E01.mkv` (no season folder) it reads `<library root>/tvshow.nfo`, and never `Show/tvshow.nfo`.
- **Failure scenario:** Genres, age rating and studio from `Show/tvshow.nfo` are never used. Worse, a stray `tvshow.nfo` at the library root gets applied to every flat show.
- **Smallest fix:** Append both `os.path.join(folder, "tvshow.nfo")` and the parent one, in that order.
- **Confidence:** confirmed by reading.

### P5. Trakt: network errors crash the plugin with a traceback, which users see

Status: Fixed in `e2f7732`.

- **File:** `plugins/trakt/main.py:136-142, 457-458`
- **Category:** Bug (unhandled input/condition).
- **Problem:** `call()` turns only `HTTPError` into `TraktError`. A timeout, DNS failure or refused connection (`URLError`, `socket.timeout`) crashes the program. In `on_call` the catch is only `TraktError`, so the panel buttons show "The plugin failed: exit 1: Traceback …" (`src/handlers.rs:1122`).
- **Failure scenario:** Reproduced with an unreachable API: a long traceback and exit 1. While Trakt is down, every playback event logs a traceback, and "Connect Trakt" shows a stack trace.
- **Smallest fix:** In `call()`, add `except (urllib.error.URLError, OSError) as e: raise TraktError(0, str(e))`. Keep `0` out of the 400/401 "disconnect" branch.
- **Confidence:** confirmed (reproduced).

### P6. Webhook: a redirect turns the POST into a GET without the message, and it still counts as "sent"

Status: Fixed in `e2f7732`.

- **File:** `plugins/webhook-notify/main.py:25-28`
- **Category:** Bug.
- **Problem:** urllib follows 301/302/303 on a POST as a GET and drops the body.
- **Failure scenario:** Reproduced. `/redir` (302 → `/ok`) → the server log shows `GET /ok (no body)`, and the plugin answers `{"ok": true, "sent": 1}`. Typical real cause: a Home Assistant or ntfy URL entered as `http://` that redirects to `https://`. The user thinks it works, but no message ever arrives.
- **Smallest fix:** Count a send only if the final URL is the one asked for (`r.geturl() == url`), or refuse redirects with a small `HTTPRedirectHandler` subclass. Log "redirected to X; put X in the settings".
- **Confidence:** confirmed (reproduced).

### P7. Webhook: invite links and email addresses go to the webhook

Status: Fixed in `e2f7732` (also drops the invited email from the plain-JSON body; the admin's own invite note is still sent).

- **File:** `plugins/webhook-notify/main.py:15, 49`; `src/routes.rs:1785` and `src/handlers.rs:217` (event data)
- **Category:** Risk (secret/privacy leak).
- **Problem:** In JSON mode the whole `data` is posted. For `user.invited` that includes `url`, which is the invite link and is enough to create an account, plus `email` and `note`. For `user.joined` it includes the invite `code`. In Discord mode the text `"{by} invited {email}"` puts the invitee's email into the channel.
- **Failure scenario:** An admin enables `user.invited` for a Discord or ntfy channel that other people can read. Anyone in the channel can use the invite link before the invitee does.
- **Smallest fix:** Drop `url` and `code` (and the email in Discord mode) before sending: `data = {k: v for k, v in data.items() if k not in ("url", "invite", "code")}`.
- **Confidence:** confirmed by reading (only if the admin turns on that event; `user.invited` is off by default, `user.joined` is on).

## Nice to have

### P8. Trakt: the stale-lock cleanup can delete a lock that is still held

Status: Postponed (nice to have; rare).

- **File:** `plugins/trakt/main.py:74-89`
- **Category:** Scale (race between two runs).
- **Problem:** A lock older than 60 s is deleted. But a holder can legitimately run up to 90 s (plugin limit): an import does a refresh plus two GETs with up to 30 s each. The check (`getmtime`) and the delete (`remove`) are also two separate steps, so between them another run can delete a fresh lock.
- **Failure scenario:** A slow "Bring in my Trakt history" (more than 60 s) is running. A playback event deletes the lock, and both runs `load()` and `save()` `tokens.json`. The last writer wins, so a freshly rotated refresh token can be lost, which leads to the disconnect in P1.
- **Smallest fix:** Raise the stale age above the plugin timeout (`> 120`), or use `fcntl.flock` on an open file. The OS releases that lock when the process dies, so no stale-lock logic is needed.
- **Confidence:** plausible.

### P9. Trakt: `tokens.json` is world-readable plain text in the shared config folder

Status: Postponed (nice to have; low risk on a single-household NAS).

- **File:** `plugins/trakt/main.py:30, 110-114`
- **Category:** Risk (secret storage).
- **Problem:** Access and refresh tokens are written with the default umask, mode 0644 (seen: `-rw-r--r-- tokens.json`). The file sits in `/volume1/docker/lichtspiel/plugins/trakt/`, which may be reachable over SMB. The tokens are not printed to logs; I checked the error paths and the server's plugin log.
- **Failure scenario:** Any NAS account with read access to the `docker` share can copy the tokens and act on the users' Trakt accounts.
- **Smallest fix:** `os.chmod(tmp, 0o600)` before `os.replace` in `save()`. Do D6 as well, or root owns everything anyway.
- **Confidence:** plausible (depends on the share's permissions).

### P10. Webhook: any signed-in user can fire test messages without limit

Status: Postponed (nice to have; only signed-in users).

- **File:** `src/routes.rs:1836` → `src/handlers.rs:1094`; `plugins/webhook-notify/main.py:42`
- **Category:** Risk (abuse).
- **Problem:** `POST /api/plugins/{id}/call/{action}` has no admin check. Webhook-notify treats every `api.call` (any action name) as "send a test message". Each call starts a Python process that can run up to 15 s.
- **Failure scenario:** A non-admin user (or a script with their token) loops the call → the Discord or ntfy channel is spammed, and the NAS starts many processes.
- **Smallest fix:** In webhook-notify, answer `api.call` only when `data.get("admin")` is true; the server already sends `admin`.
- **Confidence:** confirmed by reading.

### D9. `.gitignore` gaps: `android/build/` and `__pycache__/`

Status: Fixed in `cd9586b` (.gitignore); `2c4141c` (.dockerignore `**/__pycache__`).

- **File:** `.gitignore:1-4`; `clients/lichtspiel/.gitignore` (`/build/` matches only `clients/lichtspiel/build/`); `.dockerignore:1-7`
- **Category:** Lean / hygiene.
- **Problem:** `clients/lichtspiel/android/build/` (Gradle's `reports/problems/problems-report.html`, 132 KB) is untracked and not ignored (`git check-ignore` prints nothing). `__pycache__/` is ignored in neither `.gitignore` nor `.dockerignore`. Running Python on a plugin in the repo creates `plugins/*/__pycache__/`, which `COPY plugins` then puts into the image. My own `py_compile` run created these folders; I deleted them, and the tree is back to its starting state.
- **Failure scenario:** `git add -A` commits Gradle build output. Stale `.pyc` files end up in the image.
- **Smallest fix:** Add `/android/build/` to `clients/lichtspiel/.gitignore` (or `**/build/`). Add `__pycache__/` to both the root `.gitignore` and `.dockerignore`.
- **Confidence:** confirmed.

### D10. The build can pull different dependencies or a different toolchain than tested locally

Status: Postponed (nice to have).

- **File:** `Dockerfile:4, 14, 22, 26`
- **Category:** Risk (reproducibility).
- **Problem:** `rust:1-slim-bookworm` floats to every new Rust release, and the `cargo build`/`cargo test` calls have no `--locked`. If `Cargo.toml` changes without a matching `Cargo.lock` commit, cargo silently resolves new versions in CI.
- **Failure scenario:** A dependency bump is committed without the lock file → CI builds versions that nobody tested on a desktop, or a new Rust release breaks the build on a push that changed nothing.
- **Smallest fix:** Add `--locked` to the three cargo calls. Optionally pin `rust:1.xx-slim-bookworm`.
- **Confidence:** plausible.

## Checked, no finding
- **XXE in nfo-reader:** `ElementTree` does not load external entities. A test file with `<!ENTITY x SYSTEM "file:///etc/hosts">` gave no metadata and no file content.
- **Billion laughs in nfo-reader:** In the image (Debian bookworm, Python 3.11, expat 2.5) expat's built-in limit should stop it. I could not confirm the expat version without Docker. On a host with an old expat (macOS system Python 3.9 / expat 2.2.8) a hostile `movie.nfo` took 15.9 s of CPU and a lot of memory, but the plugin's 10 s limit kills it. Low risk, because .nfo files come from the user's own media folder. The Python docs say expat ≥ 2.4.1 protects against it; the docs did not show that table.
- **SSRF to the LAN in webhook-notify:** Only admins can set `urls` (`PUT /api/plugins/{id}/settings` checks admin), and posting to Home Assistant on the LAN is the purpose. Not a finding.
- **Secrets in CI logs:** `deploy.yml` uses no secrets. On failure it prints `docker logs` and `server.log`. I grepped the log calls and found no tokens or passwords (Plex tokens go in a header, not in URLs).
- **Two pushes at once:** The Gitea runner's default `capacity` is 1, so jobs are queued (Gitea runner docs, `config.go`). It becomes a race only if capacity is raised. No `concurrency:` group is set; I couldn't confirm from the docs whether Gitea supports it in the installed version.
- **Layer caching:** apt first, then a dependency build with an empty `main.rs`, then the sources, with `GIT_SHA` declared late. The order is right. `build.rs` tracks `GIT_SHA`.
- **`LICHTSPIEL_BUNDLED_PLUGINS`:** `/opt/lichtspiel/plugins` matches `COPY plugins /opt/lichtspiel/plugins` and the fallback list. The path is fine; the update path is not (D3).

## Verdict
Fix D1 first (a failed deploy can leave the server down), then D2 (turning on HTTPS stops every deploy). Then fix D3 before any plugin fix, or the plugin fixes never reach the NAS.

Lean: about 15 lines could go if D8 merges the compose and `deploy.yml` run setups; no dependencies can be dropped.

Not checked: nothing was run inside the Docker image or on the NAS (no Docker here). I didn't read the Rust server beyond the plugin, TLS, bind and GDM call paths. The Flutter client was read only for discovery. Trakt's official API docs were not reachable (P1 relies on secondary sources). The `previous` rollback after a DB schema change wasn't tested (D4). 3 smaller items were left out: in nfo-reader every new item starts one Python process in series; in `fire` the plugins run one after another, so webhook-notify waits behind trakt; and the server writes stdin before it starts reading stdout (no deadlock with the bundled plugins).
