# Web app review, 2026-11-15

Status: all findings handled, see [the review overview](../review-2026-11-15.md).

Branch `review/ponytail-fixes`, audited 2026-11-15. No code was changed.

**What this is:** a plain-JS single-page app (`web/`) compiled into the Rust server. It signs people in, browses libraries, plays video (direct file, or progressive MP4 from ffmpeg; no hls.js or MediaSource in this code), and has the admin pages. The token sits in localStorage/sessionStorage and goes out as `X-Token` on API calls and as `?token=` on every media URL.

**Load I assumed:** a home NAS with a few to about ten users, libraries of 5k to 50k items (a music library can reach 50k+ songs), and one admin who often leaves a tab open for hours while scans and metadata jobs run.

**Labels:** *confirmed* means I traced it in the code and the failure follows directly from it. *Plausible* means it depends on browser or network behaviour I could not run here.

## Must fix

### W1. Slow page loads overwrite the page you are on now (race)

Status: Fixed in `8c91a1e`.

- **Where:** `web/pages.js:1770-1807` (`render`, no check for a newer navigation). Examples: `web/app.js:456-460` (`searchPage`), `web/app.js:701` (`sectionPage` awaits, then `set()`), `web/app.js:846` (cleanup listener added after the await).
- **Category:** race condition / bug.
- **Problem:** every hash change starts `render()`. Each page function awaits the server and then calls `set()`, which replaces `#main`. Nothing checks whether the user has moved on in the meantime.
- **Failure scenario:**
  1. The search box sets the hash 300 ms after typing stops. Type "star", pause, type " wars". If the "star" answer arrives after "star wars", the page shows "Search: star" while the box says "star wars".
  2. Click a big library, then click Home before it loads. Home draws, then the library replaces it while the address says `#/`.
  3. In case 2, `sectionPage` adds its `scroll` listeners and its `hashchange {once}` cleanup after the hash has already changed. Those listeners stay until the next navigation after that.
- **Smallest fix:** one `AbortController` per navigation, used only for GETs:
  - in `render`: `if (S.nav) S.nav.abort(); S.nav = new AbortController();`
  - in `api()`: `if (method === 'GET' && S.nav) opt.signal = S.nav.signal;`
  - in render's `catch` and in `loadPage`'s `catch`: `if (e.name === 'AbortError') return;`

  POSTs (timeline reports) are left alone, so a "stopped" report is never cut off.
- **Confidence:** confirmed.

### W2. "Sign out" does not end the session on the server

Status: Fixed in `8c91a1e`.

- **Where:** `web/app.js:97` (`logout`), `web/app.js:217` (the menu item "Sign out" runs `logout`). Compare `web/app.js:168-171` (`switchUser` calls `POST /api/logout`). The server side is `src/routes.rs:297-302`.
- **Category:** token handling / security.
- **Problem:** "Sign out" only deletes the token from browser storage. The server keeps it valid. Only "Switch user" calls `/api/logout`, which really deletes the token.
- **Failure scenario:** someone signs out on a shared or borrowed computer. Anyone who copied the token keeps full access, for example from a proxy log or a saved download link (see W3). The token also still shows under Settings → Devices as active.
- **Smallest fix:** make the menu entry use `switchUser` (it already calls `/api/logout` and then `logout()`). Or start `logout()` with `api('POST','/api/logout').catch(()=>{})` when it is not reached from a 401.
- **Confidence:** confirmed.

## Should fix

### W3. The long-lived session token is in every picture, video, subtitle and download address

Status: Fixed in `23857bf` (web and server: short-lived signed tickets); `fa82202` (Flutter client: X-Token header).

- **Where:** `web/app.js:63` (`withTok`). Used at `app.js:265` (posters), `app.js:1778/1782` (video src), `app.js:1797` (subtitle tracks), `app.js:2207` (media-session artwork handed to the operating system), `downloads.js:15` (`saveFile`), `pages.js:1837` (log export).
- **Category:** token handling.
- **Problem:** `?token=` carries the same token that signs in to the full API, with no expiry from the browser side. Query strings are written to reverse-proxy access logs (for example the Synology reverse proxy or nginx in front of the NAS). They also stay in the browser's download list, and "Copy video address" puts the token on the clipboard.
- **Failure scenario:** an admin reads the proxy log, or a family member copies a download link out of the download list. Either one now has that user's account, and because of W2 it is still valid after "Sign out". The Rust server's own log only records `ctx.path` (`src/server.rs:2503`), so this mainly leaks through the proxy, the browser and the OS.
- **Smallest fix:** first fix W2. Then either sign media URLs with a short-lived, read-only media token from the server, or set an HttpOnly same-site cookie at sign-in so media requests need no query token. Both need a server change, so this needs agreement with the Rust audit.
- **Confidence:** the token in URLs is confirmed. That it lands in a given proxy log is plausible.

### W4. Redrawing a library page leaks listeners and keeps whole old grids in memory

Status: Fixed in `8c91a1e`.

- **Where:** `web/app.js:839-846` (two window `scroll` listeners per `sectionPage`, removed only on `hashchange`). `web/app.js:1155-1161` (`pollActivity` calls `render()` on `#/section/…` every ≥8 s while details arrive). `web/pages.js:1659` (`reloadSections` re-renders too).
- **Category:** memory / timer leak, slow path.
- **Problem:** a re-render of the same hash fires no `hashchange`, so the old page's `onScroll`/`onPos` listeners and its `IntersectionObserver` stay alive. Through `showPos` they keep a reference to the old grid with all its cards.
- **Failure scenario:** an admin keeps a library tab open at the top of the page during a "Refresh all metadata" of 10k titles that takes hours. Every 8 s another full grid (one placeholder per title) stays in memory, and one more pair of scroll handlers runs `elementFromPoint` on each scroll. That is about 450 grids per hour, so the tab grows by hundreds of MB and scrolling gets slower.
- **Smallest fix:** keep the cleanup in one module-level variable. At the start of `sectionPage`, run the previous cleanup: `if (LIBCLEAN) LIBCLEAN(); LIBCLEAN = () => { more.disconnect(); closePanel(); removeEventListener('scroll', onScroll); removeEventListener('scroll', onPos); saveLibPos(); };`. The `hashchange` handler then just calls `LIBCLEAN`.
- **Confidence:** confirmed (listeners and retention are in the code; the MB figure is an estimate).

### W5. Many button actions fail without telling the user

Status: Fixed in `8c91a1e`.

- **Where:** for example `web/app.js:809` (Scan now), `app.js:951-953` (watched, favorite and watchlist toggles), `app.js:302-303/313/355` (pick bar), `app.js:476` (`dropBtn` entries), `web/pages.js:96-100` (playlist rename, pin, share, delete), `pages.js:112`, `pages.js:1461-1462`, `web/downloads.js:112/115/129`. There is no `unhandledrejection` handler anywhere (grep).
- **Category:** missing error handling.
- **Problem:** these `async` click handlers `await api(...)` with no `catch`. When the server answers with an error, the promise is rejected and nobody sees it.
- **Failure scenario:** the server is restarting (every push to `main` redeploys it) or a request returns 403/500. The user clicks "Mark watched" and nothing happens: no toast, and the icon does not change.
- **Smallest fix:** one global line in `app.js`: `window.addEventListener('unhandledrejection', e => { if (e.reason && e.reason.name !== 'AbortError') toast(e.reason.message || String(e.reason), 6000); });`. This covers all of them at once.
- **Confidence:** confirmed.

### W6. A converted stream that ends early marks the title as watched and starts the next one

Status: Fixed in `8c91a1e`.

- **Where:** `web/app.js:1991-1996` (`ended` → `report('stopped', duration()*1000)` → `upNext()`).
- **Category:** bug (data written wrong).
- **Problem:** the `ended` event fires when "the end of the media was reached **or no further data is available**" (MDN). For a progressive transcode, a stream that is closed cleanly before the end looks exactly like the end. The handler then reports the full duration as the position.
- **Failure scenario:** ffmpeg crashes, or a transcode is killed (owner stops it, the transcode limit is reached, the server restarts) 20 minutes into a film. The browser fires `ended`, the film is saved as watched at 100 %, and the next episode counts down.
- **Smallest fix:** in the `ended` handler, report `position()` instead of `duration()`. When `duration() - position() > 60`, show an error toast and keep the player open instead of calling `upNext()`.
- **Docs:** MDN `HTMLMediaElement: ended event` (/mdn/content, files/en-us/web/api/htmlmediaelement/ended_event).
- **Confidence:** plausible. The handler logic is confirmed; whether the server closes the stream cleanly on ffmpeg failure is not verified.

### W7. Theme music starts on the wrong page and restarts on every redraw

Status: Fixed in `8c91a1e`; follow-up `17af37a` (plays on the next visit after a brief connection drop).

- **Where:** `web/pages.js:1782` (`stopTheme(); await itemPage(); startTheme(id)`), `pages.js:1759-1768`. Triggered also by `app.js:1161` (`pollActivity` → `render`) and `app.js:2227` (`closePlayer` → `render`).
- **Category:** race condition.
- **Problem:** `startTheme` runs after the await without checking that the item page is still shown.
- **Failure scenario:**
  1. Open a movie and press Back before it loads. The hashchange `stopTheme` has already run, then `startTheme` starts the music on Home, and nothing stops it until it ends.
  2. On a movie page, each background "details finished" refresh fades the theme and starts it again from the beginning.
  3. Closing the player starts the theme again right after the film.
- **Smallest fix:** in the `item` case, call `if (location.hash.startsWith('#/item/' + parts[1])) startTheme(parts[1]);`. In `stopTheme`, keep `THEME.id` when the next page is the same item. Or give `startTheme` a `played` set, so a theme plays only once per item per visit.
- **Confidence:** confirmed.

### W8. The playlist page loads and draws every item at once

Status: Fixed in `f1dce91` (the page loads rows in pages; the server already paged).

- **Where:** `web/pages.js:78` and `web/pages.js:107-113`. The server returns everything when no `size` is given (`src/routes.rs:1514-1531`, `page(ctx,&ids)` with no `size`).
- **Category:** slow path on big libraries.
- **Problem:** a smart playlist such as "all unwatched episodes" can match tens of thousands of items. The page fetches the full JSON for all of them (`item_json`), builds one row per item, and reloads the whole list after every ↑/↓ move.
- **Failure scenario:** a smart playlist that matches 20k episodes takes seconds to answer and draw, and each reorder click repeats that.
- **Smallest fix:** reuse the library page's paging. Ask for `start`/`size=120` and load more on scroll with the same `IntersectionObserver` pattern as `sectionPage`. `playPlaylist` can keep fetching everything.
- **Confidence:** the unpaged request is confirmed; the slowness is plausible (not measured).

### W9. The import progress loop never stops and runs again on every visit

Status: Fixed in `8c91a1e`.

- **Where:** `web/pages.js:441-447` (`waitDone`). Compare the Plex sync loop at `pages.js:345-352`, which checks `lastBox.isConnected`.
- **Category:** timer leak.
- **Problem:** `waitDone` polls every 1.5 s for up to an hour with no page check. Every time the Libraries page is drawn during an import, it starts another loop.
- **Failure scenario:** an admin opens Libraries five times during a 30-minute import. Five loops now poll `/api/import/old-server` every 1.5 s from any page. At the end, "Import finished" toasts five times and the chrome is redrawn five times.
- **Smallest fix:** add `if (!lastBox.isConnected) return;` after the sleep, exactly as the Plex sync loop does.
- **Confidence:** confirmed.

### W10. The Downloads page stops updating after a dialog or a network error

Status: Fixed in `8c91a1e`.

- **Where:** `web/downloads.js:132`.
- **Category:** missing error handling / timer.
- **Problem:** when the 2 s timer fires while a modal is open, or when `refresh()` fails, it does not schedule itself again.
- **Failure scenario:** click ✕ on a converting download, and its "Stop converting?" dialog is open when the timer fires. Press Cancel, and the list stays at "Converting 40 %" until you leave the page. A single network error causes the same.
- **Smallest fix:** when busy, always schedule the next tick and skip only the redraw: `DL.timer = setTimeout(() => { if (!listBox.isConnected) return; if (document.querySelector('.modal')) return refreshLater(); refresh().catch(refreshLater); }, 2000)`. Or just move the modal check inside `refresh`.
- **Confidence:** confirmed.

### W12. With "Level the volume" on, a video can play without sound

Status: Postponed (nice to have; needs Safari to reproduce).

- **Where:** `web/app.js:1741-1754` (`AudioContext` created in `load()`, after awaits), `app.js:2101` (`togglePlay` never resumes the context).
- **Category:** browser API.
- **Problem:** once `createMediaElementSource(video)` runs, all sound goes through the `AudioContext`. A context created outside a user gesture starts `suspended` (MDN Web Audio best practices). Here it is created after `await GET(...)`, and for `#/play/<id>` links with no gesture at all.
- **Failure scenario:** open a `#/play/123` link with leveling on. Autoplay is blocked, so the user clicks ▶. The picture plays but the context stays suspended and there is no sound. Safari is the most likely to show this.
- **Smallest fix:** in the video `play` listener: `if (LEVEL.ctx && LEVEL.ctx.state === 'suspended') LEVEL.ctx.resume();`. That call runs inside the user's click.
- **Docs:** MDN "Web Audio API best practices – Autoplay policy" (/mdn/content, files/en-us/web/api/web_audio_api/best_practices).
- **Confidence:** plausible (depends on each browser's activation rules).

### W13. Two quick seeks while converting can land on the older position

Status: Postponed (nice to have).

- **Where:** `web/app.js:1755-1769` (`load` only checks `P.it !== it`), `app.js:1717-1720`.
- **Category:** race condition.
- **Problem:** two `load()` calls for the same item both pass the check. Whichever `/decision` answer arrives last sets `video.src`, and each one starts its own ffmpeg stream.
- **Failure scenario:** click the seek bar twice quickly (or press Home and then 5) during a transcode. If the first decision answers last, playback jumps back to the first position.
- **Smallest fix:** `const seq = ++P.loadSeq;` at the start of `load`, and `if (P.it !== it || seq !== P.loadSeq) return;` after the await.
- **Confidence:** plausible (the answers are usually in order).

### W14. A huge library makes one empty card per title up front

Status: Fixed on 2026-11-21: a library of more than 2,000 titles has only the cards around the screen, with a block above and below as tall as the rows they stand for (`pickGrid()` in `web/app.js`).

- **Where:** `web/app.js:732-733` (`grid._reserve(total - …)` and `observe` on every placeholder), `app.js:400-407`.
- **Category:** slow path.
- **Problem:** the "Songs" view of a 80k-track music library builds 80k placeholder cards (about 320k elements) and observes each one before anything else happens.
- **Failure scenario:** opening such a view freezes the tab for seconds and uses a lot of memory, especially on a phone.
- **Smallest fix:** cap the reserved placeholders (for example 3k ahead of the loaded range) and keep one tall spacer element for the rest. Or measure first and leave it if a 20k library is acceptable.
- **Confidence:** plausible (not measured).
