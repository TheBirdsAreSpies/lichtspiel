## Before deploying to main

Every push to `main` deploys to the NAS. In this order where it matters:

1. Run `sudo chown -R 1026:100` on the config folder (for example `/volume1/docker/lichtspiel`). The container no longer runs as root, and the deploy stops at the `/config` check if the folder is not writable (`cd9586b`).
2. Hardware transcoding: `--group-add` for `/dev/dri` is now added by the deploy itself (`e5b860a`). After the deploy, only check that the dashboard still shows "hw".
3. Update Lichtspiel on the relay computer before the NAS. A new home server refuses a relay that can't prove the secret (`c4f405f`).
4. A rollback signs everyone out: sign-ins are stored as fingerprints (`17af37a`) and the older version can't read them. The rollback step says so (`e5b860a`).
5. Third-party browser clients on other websites stop working: there is no `Access-Control-Allow-Origin` any more (`c4f405f`).
6. Links that point outside all library folders are no longer scanned or played; links from one library into another are kept (`c4f405f`, `bd1f462`).
7. "Poster from URL" can't fetch LAN or localhost addresses any more (`c4f405f`).
8. Tailscale or CGNAT clients (100.64.0.0/10) must be added to the "home network" setting to be answered by discovery (`17af37a`).
9. Open the web app once after the deploy and check the browser console for CSP errors (blocked scripts or frames).
10. A reverse proxy on plain http must keep the `Host` header (or use https); otherwise the web app's own POSTs get 403 (`bd1f462`).
11. The first start queues every movie and show without details for one round of online lookups (`bd1f462`).
12. Folder watching now looks every 60 seconds instead of 15 (`bd1f462`, `c68f7f5`).

Outside the code: port 8484 is open to the internet over plain http, so passwords and tokens cross the internet unencrypted. Put it behind the DSM reverse proxy with a Let's Encrypt certificate, or turn on HTTPS in Lichtspiel, and close the plain port in the router.

## Known limits

- Relay: the link itself is still plain TCP (no TLS); both sides prove the secret (X5).
- The server accepted `?token=` in addresses for older clients and scripts (X7). Since 2026-11-21 it no longer does; links use `?ticket=`.
- Request headers: no overall time limit for a client that trickles bytes slowly; each one holds one thread (X2).
- Discovery has no rate limit; it answers only home-network senders (X12).
- Broken posters inside media folders are left as they are (S1); the race between the idle check and the delete in clean-up is not addressed (S2); relayed callers show as "not trusted" (S3).
- The S4 tests run on Unix only.
- A stale page waiting on a non-GET request can still draw late (W1). A stream that ends less than 60 s before the end still counts as finished (W6).
- HLS streams per person: only streams idle for more than 20 s make room, so an account shared by 5 or more devices that all play keeps every stream; `max_transcodes` still bounds the work (S-R4). Progressive remux streams have no per-person cap.
- The ▶ queue on a playlist row only holds the rows loaded so far ("Play all" fetches everything).
- A plugin that starts a program which keeps the plugin's input open leaves one thread waiting until that program ends; the request no longer waits (S13).
- Client: dart:io can't close a socket stuck in a TLS handshake; after the timeout that socket stays open. An IPv6 address typed without brackets is not handled (`0d48314`).
- Client: if media_kit on some platform ignores the HLS request headers, playback there relies on the ticket in the HLS addresses and could fail after 5–6 hours. Not run against a real server (`fa82202`).
- Web: ticket renewal during a very long playback is not tested in a real browser (`23857bf`).
- Client: a body that stalls after the headers arrived isn't cut off (C-R2).
- Client: a download that fails before the dialog's first frame leaves the dialog open until "Abbrechen" (C-R3).
- Restore doesn't run `Db::after_load` (old default server name renamed, default playlists created); that happens at the next start.
- A Plex sync that runs during a restore can write sync state for the replaced library.
- A reverse proxy on plain http that rewrites `Host` gets 403 on the web app's own POSTs (S-R3); keep `Host` or use https.

## Client connection problem of 2026-11-15

The app could not connect and showed one generic error. Cause: the address was entered as `https://` while the server speaks plain http on that port, the app had no timeouts (the TLS handshake hung), and every failure gave the same message. Fixed in `0d48314` (10 s limit, German error texts with the cause, IPv6 default port) and `2c4141c` (https on the plain port fails at once). Since `ba75f0d` the https → http fallback only happens inside the home network (C-R1).
